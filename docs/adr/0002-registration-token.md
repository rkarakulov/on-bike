# 0002. Токен регистрации для входа после подтверждения e-mail

- Статус: Accepted
- Дата: 2026-10-22

## Контекст

Прототип онбординга (V-09) требует, чтобы после подтверждения e-mail райдер попадал в приложение без
повторного ввода пароля. Архитектурный спайн (AD-28) запрещает выдавать неподтверждённому аккаунту
полноценные токены. Подтверждение происходит по ссылке из письма — часто в другом приложении или на
другом устройстве, — поэтому сессию нельзя просто вернуть из `confirm`.

Ограничение безопасности: в БД хранятся только хеши токенов, а письмо отправляет worker из outbox,
поэтому сырой случайный токен ссылки некуда положить между HTTP-запросом и задачей.

## Решение

1. При регистрации выдаётся **токен регистрации** (32 случайных байта, base64url; в БД — sha256).
   Он не является access-токеном: годится только для `POST /v1/auth/registration/poll` и
   `POST /v1/auth/verification/resend` и **один раз** обменивается на сессию после подтверждения
   (условный `UPDATE … WHERE consumed_at IS NULL … RETURNING` в одной транзакции со вставкой сессии).
2. Срок токена регистрации — скользящий: равен сроку текущей ссылки (24 ч) и продлевается каждым
   повтором письма.
3. **Токен ссылки** = `base64url(HMAC-SHA256(EMAIL_TOKEN_SECRET, "email-verify:" + id строки))`,
   в БД — sha256 от него. Worker пересобирает ссылку по id из outbox: сырого токена нет ни в outbox,
   ни в Redis, ни в логах, а ретрай задачи даёт ту же ссылку.
4. Открытие ссылки (`GET`) ничего не меняет; активация — только `POST confirm`.

## Альтернативы

- **Сессия сразу при регистрации с флагом «не подтверждён»** — нарушает AD-28, каждый эндпоинт должен
  помнить про флаг.
- **Сессия в ответ на `confirm`** — не работает, когда ссылку открыли на другом устройстве или в
  браузере: сессия окажется не там, где регистрировались.
- **Случайный токен ссылки в payload outbox** — сырой секрет в БД и в Redis (BullMQ), против правила
  «в БД только хеши».
- **Повторный вход по паролю после подтверждения** — противоречит V-09.

## Последствия

- Плюсы: AD-28 соблюдён (до подтверждения у клиента нет токенов доступа), V-09 выполняется на
  устройстве регистрации; утечка таблиц не даёт рабочих ссылок и сессий.
- Минусы: `EMAIL_TOKEN_SECRET` — ещё один секрет; его смена инвалидирует все неотправленные и
  неиспользованные ссылки (пользователь запрашивает новую).
- Потерянный ответ `poll` (обрыв после коммита) — повтор получает 401; клиент показывает
  «E-mail подтверждён. Войдите» (вход по паролю — слайс 2).
- Пересмотреть при появлении входа по паролю и refresh-ротации (слайс 2) и universal links (слайс 5).
